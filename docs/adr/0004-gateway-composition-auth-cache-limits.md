# ADR-0004. Розширення шлюзу: складений запит, автентифікація, кеш, обмеження частоти

## Статус

Accepted (2026-10-27). Розвиває ADR-0002 (шлюз на Ocelot); ЛР3.

## Контекст

Після ЛР2 шлюз лише маршрутизує. Клієнту, щоб показати екран «Тренування», треба 3 запити (позиція каталогу, розклад,
профіль), а сам шлюз: не має таймаутів (Ocelot чекає до 90 с), не перевіряє токени (кожен сервіс довіряє будь-кому, хто до
нього достукався), нічого не кешує і не захищений від потоку запитів. Правило ЛР3: **поведінка наявних маршрутів не змінюється**.

## Рішення

| # | Питання | Рішення |
|---|---|---|
| 1 | Складений запит | `GET /api/v1/screens/training/{itemId}` — власний ендпоінт шлюзу (поза Ocelot). Три виклики паралельно (`Task.WhenAll`): Catalog (позиція), Schedule (тренування позиції), Auth (`/users/me`). Типізовані `HttpClient` з таймаутом 2 с на кожен. |
| 2 | Часткова відповідь | Catalog — **обов'язкове ядро**: недоступний → `503`, не знайдено → `404` (ProblemDetails). Schedule/Auth — **необов'язкові**: їх збій не валить екран; у відповіді `partial: true`, `unavailable: ["sessions"]`, заголовок `X-Partial-Response: true`, відсутній блок = `null`. Порожній список тренувань (`[]`) ≠ «сервіс недоступний» (`null`). |
| 3 | Таймаути | Клієнти складеного запиту — 2 с; проксійовані виклики Ocelot — 5 с (`ProxyTimeoutMiddleware` підміняє `RequestAborted` на токен із дедлайном) → `504` ProblemDetails; порожня 5xx від Ocelot → `503`; health-перевірки — 1 с. Значення — в `Gateway:Timeouts`. |
| 4 | Автентифікація | JWT перевіряє **шлюз** (підпис, issuer, audience, строк, `ClockSkew` 30 с). Захищені: екран, `/api/v1/users/**`, зміни каталогу (POST/PUT/PATCH/DELETE). Решта — відкрита як було. Далі йдуть `Authorization`, `X-User-Id`, `X-User-Roles`; клієнтські `X-User-*` **завжди видаляються**. |
| 5 | Закриті порти | У `docker-compose.yml` назовні публікуються лише шлюз (5000) і MySQL; Auth/Catalog/Monolith/Schedule — лише у внутрішній мережі. Для налагодження — `docker-compose.debug.yml`. Локально сервіси слухають 127.0.0.1. |
| 6 | Кеш | `IMemoryCache`, лише **GET /api/v1/catalog/**** (спільні дані). Ключ `catalog:http:{шлях}{query}`, TTL 60 с (`Gateway:Cache`). Заголовок `X-Cache: HIT/MISS`, статистика — `GET /gateway/cache`. Складений запит бере позицію каталогу з того самого кешу. |
| 7 | Інвалідизація | Успішна зміна каталогу (2xx на POST/PUT/PATCH/DELETE через шлюз) скидає весь регіон (`CancellationChangeToken`). TTL — страховка на випадок змін повз шлюз. Токен береться ДО запиту, тож відповідь, застаріла під час запиту, у кеш не потрапить. |
| 8 | Ліміти | `Microsoft.AspNetCore.RateLimiting`: вхід/реєстрація — fixed window 5/хв за IP; авторизовані — token bucket за **користувачем** (burst 100, +120/хв); анонім — fixed window 100/хв за **IP**. `/health`, Swagger — без ліміту. Відповідь `429` + `Retry-After` + ProblemDetails. |
| 9 | Помилки | Усі помилки шлюзу — `application/problem+json` (RFC 9457) із `correlationId`: 401, 429, 404, 503, 504, 500 (`IExceptionHandler`). Власні відповіді сервісів (з тілом) проходять без змін. |
| 10 | Документація | Swagger (`/swagger`) описує складений запит: приклади, коди 200/401/404/429/503, схему Bearer, `X-Partial-Response`. |
| 11 | Здоров'я | `GET /health` перевіряє шлюз і залежності (`/health` кожного сервісу, 1 с): `200 {"status":"ok"}` або `503 {"status":"degraded","dependencies":{…}}`. |

## Розглянуті варіанти

* **Ocelot Aggregator / QoS (Polly) замість власного коду.** `+` менше коду; `−` Aggregator не вміє «обов'язкове vs необов'язкове»
  й часткову відповідь з явним маркером; QoS-пакет — додаткова залежність. Обрано власний ендпоінт + типізовані клієнти.
  Якщо Ocelot не поважатиме дедлайн у `RequestAborted`, резерв — `Ocelot.Provider.Polly` (`QoSOptions.TimeoutValue`).
* **Redis-кеш.** `+` спільний між екземплярами; `−` ще одна інфраструктура. Для одного екземпляра шлюзу достатньо пам'яті
  процесу; при масштабуванні — перехід на розподілений кеш.
* **Довіра сервісів до токена без шлюзу (перевірка в кожному).** `−` дублювання ключа/логіки в кожному сервісі. Обрано
  перевірку на межі.

## Наслідки

**Отримали:** один запит замість трьох; швидкий відказ замість зависання; сервіси недоступні в обхід шлюзу; менше навантаження
на Catalog; захист входу від підбору паролів; єдиний формат помилок.

**Заплатили / обмеження:**
* **Ідентифікатор користувача Auth ≠ `Person.Id` моноліту.** Тому «мої записи» зі Schedule у складений запит не входять;
  «я» береться з Auth `/users/me`. Зв'язати їх — окрема задача (ADR-0003: авторизація у Schedule/моноліті свідомо відсутня).
* Сервіси довіряють `X-User-Id` лише тому, що порти закриті; без мережевої ізоляції цей заголовок підробити можна.
* Кеш у пам'яті процесу: у кількох екземплярів шлюзу інвалідизація не поширюється — діє лише TTL.
* Лічильники лімітів теж у пам'яті процесу; за reverse proxy IP треба брати з `X-Forwarded-For` (`ForwardedHeaders`).
* Дедлайни означають, що повільна, але жива відповідь сервісу (>2 с / >5 с) відкидається.
