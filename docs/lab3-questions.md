# ЛР3 — відповіді на контрольні питання

1. **API Gateway.** Єдина точка входу для клієнтів: маршрутизація, наскрізні вимоги (автентифікація, ліміти, кеш, таймаути,
   логування, формат помилок) і, за потреби, складання відповідей з кількох сервісів. Клієнт знає одну адресу й не знає, скільки
   сервісів за нею.
2. **Чому без бізнес-логіки.** Шлюз — спільна точка для всіх команд; логіка в ньому робить його вузьким місцем змін і
   «розподіленим монолітом». Приклад: «записувати на тренування можна, лише якщо є вільні місця / ціна зі знижкою для
   абонемента» — це правило Schedule/Catalog, а не шлюзу. Шлюз лише з'єднує й захищає; тут — «чи є токен», а не «чи має
   клієнт право на це тренування».
3. **Паралельність.** Виклики незалежні, тож час відповіді ≈ найповільніший (max), а не сума. Три виклики по ~200 мс:
   паралельно ≈ 200 мс, послідовно ≈ 600 мс. Тест `Screen_CallsServicesInParallel_NotOneByOne` вимірює це.
4. **Без таймаутів.** Завислий сервіс тримає запит шлюзу (в Ocelot — до 90 с); запити накопичуються, вичерпуються потоки/з'єднання —
   лягає шлюз, а з ним і всі інші, здорові сервіси (каскадна відмова). Таймаут + швидкий `503/504` обмежують шкоду.
5. **«Даних немає» vs «сервіс недоступний».** `sessions: []` — сервіс відповів, тренувань справді немає; `sessions: null` +
   `unavailable: ["sessions"]` — ми не знаємо. Інакше клієнт покаже «розклад порожній», хоча він просто не завантажився, і
   користувач помилково вирішить, що записатися нікуди.
6. **Токен на шлюзі та `X-User-Id`.** Один раз, на межі, замість дублювання ключа й коду в кожному сервісі; недійсні запити
   не доходять до сервісів. Сервіс може довіряти `X-User-Id`, лише якщо **ніхто, крім шлюзу, не може до нього достукатися**
   (порти закриті, мережа ізольована) і шлюз сам видаляє клієнтські `X-User-*`. Інакше заголовок підробляється одним `curl`.
7. **Що кешуємо.** Лише читання каталогу: дані спільні для всіх, рідко змінюються, читаються часто, доступні анонімам. Персональне
   (`/users/me`, записи користувача) не кешуємо: ключ мав би містити користувача (кеш на кожного — мало користі), а помилка в
   ключі віддасть чужі дані одному користувачу іншому — витік.
8. **Ключ і TTL.** Ключ: `catalog:http:{шлях}{query}` — фільтри/сторінка/сортування входять у query, тож різні списки не
   плутаються; користувача в ключі немає свідомо. TTL 60 с: каталог змінюється рідко, а 60 с — припустима «неактуальність» на
   випадок змін повз шлюз; довший TTL збільшує застарілість, коротший — зменшує виграш.
9. **Навіщо інвалідизація при TTL.** TTL — лише верхня межа застарілості. Після зміни каталогу користувач очікує побачити
   її одразу, а не за хвилину. Тому успішний POST/PUT/DELETE через шлюз скидає регіон; TTL лишається страховкою.
10. **Fixed window vs token bucket.** Fixed window — «N запитів за вікно», лічильник скидається на межі; просто й жорстко,
    але на межі вікон можливий подвійний сплеск. Token bucket — відро токенів, що поповнюється з постійною швидкістю; дозволяє
    короткий сплеск і обмежує середню швидкість. Обрано: вхід — fixed window (суворо, 5/хв), авторизовані — token bucket (екран
    при старті шле кілька запитів поспіль), анонім — fixed window (простота).
11. **IP vs користувач.** Анонім не має ідентифікатора — IP єдина відмінна ознака. Авторизований — має; рахувати його за IP
    було б несправедливо (за одним IP — офіс/оператор, один спамер заблокує всіх) і обхідно (змінив IP — новий ліміт).
