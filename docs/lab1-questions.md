# ЛР1 — відповіді на контрольні питання

1. **Автентифікація vs авторизація.** Автентифікація — "хто ти" (вхід, видача JWT); авторизація — "що тобі можна"
   (роль Admin для зміни каталогу). Централізована автентифікація: токени видає лише AuthService; авторизація
   розподілена — кожен сервіс сам перевіряє роль у токені.
2. **JWT.** `Header.Payload.Signature`. Підпис захищає цілісність (payload не підмінили). Не захищає конфіденційність
   (payload лише Base64, читається будь-ким) і не захищає від крадіжки токена.
3. **Чому Catalog не питає Auth.** Підпис перевіряється локально спільним ключем: немає мережевого виклику на кожен
   запит, немає залежності від доступності Auth.
4. **Різні `Jwt:Key` / `Jwt:Audience`.** Інший ключ — підпис не збігається, 401. Інша audience — токен виданий "не для
   цього сервісу", теж 401.
5. **SHA-256 без солі.** Швидкий і детермінований: однакові паролі дають однакові хеші, працюють rainbow-таблиці й
   швидкий брутфорс. BCrypt додає унікальну сіль і навмисно повільний.
6. **Refresh-токен і ротація.** Access короткий (15 хв) — малий збиток при витоку; refresh довгий, зберігається в БД і
   може бути відкликаний. Ротація: кожен `/refresh` відкликає старий токен і видає новий — повторне використання
   старого видно як ознаку компрометації.
7. **401 vs 403.** 401 — особу не встановлено (немає/недійсний токен): `GET /users/me` без токена. 403 — особа відома,
   але прав немає: User викликає `POST /catalog/items`.
8. **DTO замість сутностей.** Сутність несе службові поля (`PasswordHash`), навігації й прив'язує контракт до схеми БД.
   DTO — стабільний, контрольований контракт.
9. **Пагінація.** `page`, `pageSize` (макс. 100), `search`, `categoryId`, `sortBy`, `desc`. Відповідь —
   `{ items, page, pageSize, totalCount }`; `totalCount` потрібен, щоб порахувати кількість сторінок.
10. **Фільтрація в БД.** Фільтри додаються до `IQueryable` до `ToListAsync()`, EF генерує один SQL з
    `WHERE/ORDER BY/LIMIT` (перевірка — логування SQL або `EXPLAIN` у Workbench). У пам'яті довелося б вантажити всю таблицю.
11. **База на сервіс.** Незалежність схем і деплою. Заборонено FK/JOIN між базами сервісів і пряме підключення до чужої БД;
    потрібні дані — через API власника.
12. **ocelot.json.** Додано `/api/v1/auth/{everything}` і `/api/v1/users/{everything}` → 5001 та
    `/api/v1/catalog/{everything}` → 5002. Конкретні маршрути стоять вище за загальний `/api/{everything}` → моноліт.
13. **Шлях запиту.** Клієнт → Gateway :5000 → CatalogService :5002 → `ItemsController` → `CatalogItemService` →
    `ItemRepository` (IQueryable) → EF Core → SQL → MySQL `miniproject_catalog` → DTO → JSON назад.
14. **Стара таблиця каталогу.** Дані одноразово скопійовано в `miniproject_catalog`. Після перемикання маршруту єдиний
    власник даних — Catalog-сервіс; таблиця моноліту застаріла й не змінюється, бо зміни в ній ніхто не побачить.

## Питання "на подумати" (п. 5.3): ціна змінилась, а позиція вже в чиємусь замовленні

Замовлення не повинно залежати від поточної ціни каталогу. Під час створення замовлення (Booking-сервіс, ЛР2) треба
**зберегти знімок**: `ItemId`, назву й ціну на момент покупки (`PriceAtOrder`). Тоді зміна ціни адміністратором впливає
лише на нові замовлення, а історичні лишаються коректними. Зв'язок із каталогом — тільки за `ItemId` (без FK між базами),
а актуальну ціну для нового замовлення Booking бере з API каталогу в момент створення.
