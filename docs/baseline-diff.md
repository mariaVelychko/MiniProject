## Свідомі відмінності (не видно в знімках, але існують)

| Що                                                | Було                                              | Стало                                                                                                                              | Чому                                                                                  |
| ------------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Тренер/клієнт перевіряються                       | SQL до `Persons` у спільній БД                    | HTTP `GET /api/users/{id}` до моноліту; якщо недоступний — `503 {"message":"Сервіс користувачів недоступний. Спробуйте пізніше."}` | Зв'язку між БД немає (вимога ЛР2). Нова відповідь можлива лише під час відмови сусіда |
| `GET /api/profile/{id}`                           | Локальне читання розкладу                         | Виклик Monolith → Schedule; якщо Schedule недоступний — `503 {"message":"Сервіс розкладу недоступний. Спробуйте пізніше."}`        | Розклад тепер у Schedule. Лише під час відмови                                        |
| Заголовок `Idempotency-Key`                       | Не підтримувався                                  | Необов'язковий для `POST /api/bookings`, `POST /api/workouts`                                                                      | Вимога ЛР2; без заголовка поведінка не змінюється                                     |
| Заголовок відповіді `X-Correlation-Id`            | Додавав шлюз                                      | Додає шлюз і сервіс (те саме значення)                                                                                             | Наскрізне логування                                                                   |
| Порядок `participantIds`                          | Порядок рядків join-таблиці (де-факто за записом) | За Id запису (порядок запису)                                                                                                      | Детермінованість                                                                      |
| Дані учасників (`GET /api/bookings/workout/{id}`) | Живі дані з `Persons`                             | Знімок на момент запису                                                                                                            | Немає доступу до чужої БД; задокументовано в ADR-0003                                 |
| Місткість при паралельних записах                 | Перевірка в пам'яті (гонка можлива)               | `SELECT … FOR UPDATE` + унікальний індекс                                                                                          | Покращення; на послідовних запитах поведінка та сама                                  |
| Авторизація                                       | Немає                                             | Немає (збережено)                                                                                                                  | Головне правило ЛР2; див. ADR-0003 «Авторизація свідомо не додано»                    |
| Скасування запису                                 | Видалення учасника (`204`)                        | Те саме (видалення, не зміна статусу)                                                                                              | Контракт не змінюється                                                                |
